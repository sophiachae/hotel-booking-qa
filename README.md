[![Playwright Tests](https://github.com/sophiachae/hotel-booking-qa/actions/workflows/playwright.yml/badge.svg?branch=main)](https://github.com/sophiachae/hotel-booking-qa/actions/workflows/playwright.yml)

📊 **최신 테스트 리포트:** https://sophiachae.github.io/hotel-booking-qa/ (main에 push할 때마다 GitHub Actions가 전체 테스트를 실행하고 갱신)

> AI가 만든 테스트 케이스를 QA 관점에서 검토·보완하고, 수동 테스트와 Playwright 자동화로 실행해 결함 11건(v1.0 6건, v1.1 5건)을 찾은 프로젝트

**테스트 대상 앱은 Claude로 만든 실습용 앱이며, 의도적으로 결함이 심어져 있습니다.** 앱 코드는 테스트 대상이므로 수정하지 않았습니다.

## 1. 프로젝트 소개

- **테스트 대상:** 호텔 검색 → 객실 선택 → 예약 → 예약 조회·취소 흐름을 갖춘 미니 웹앱 (Node.js / Express / SQLite)
  → [앱 명세 보기](docs/SPEC.md) · [변경 내역](docs/CHANGELOG.md)
- **버전:** v1.0 (예약 기능) → v1.1 (회원가입·로그인, 카카오·구글 소셜 로그인, 회원 예약). v1.1 결과는 [7장](#7-v11-회원-기능-qa)
- **목적**
  - LLM이 명세만 보고 만든 TC를 실무에서 그대로 쓸 수 있는지 확인하고, 사람이 채워야 하는 영역을 실제 결과로 정리
  - 수동 테스트와 UI·API 자동화를 함께 적용해 결함을 찾고 GitHub Issues로 관리

## 2. 진행 과정 (v1.0)

| 단계 | 한 일 | 결과 |
|---|---|---|
| 1. AI TC 생성 | 앱 명세를 LLM에 입력해 TC 생성 | 30건 |
| 2. QA 리뷰·수정 | 모호한 표기, 개발자 관점 기대결과, 명세에 없는 조건을 찾아 재작성 (수정 전 원문은 엑셀에 보존) | 13건 수정 |
| 3. 누락 TC 보완 | 화면 간 금액 일치, 기간 겹침 유형, 로그 개인정보, 더블 클릭·뒤로 가기 등 AI가 놓친 관점 추가 | 8건 추가 |
| 4. 수동 실행 | 화면·로그(`app.log`)·DB를 함께 확인하며 실행, 결함은 재현 절차와 근거를 붙여 이슈 등록 | 결함 #1~#4, #6 |
| 5. Playwright 자동화 | UI 8건 + API 18건 자동화. DB·로그 검증 포함, 알려진 결함 TC는 `test.fail()`로 표시 | 결함 #5 발견, #2 패턴 확장 |

AI가 만든 결과를 그대로 받아들이지 않고 직접 판단한 예시입니다.
- **TC 문제로 판단:** 자동화 실행에서 Fail이 난 TC-04·08·09를 검토해 결함이 아니라 AI가 명세에 없는 조건을 넘겨짚은 TC 문제로 판정
- **결함 통합:** TC-37의 중복 예약을 별도 결함으로 올리지 않고, 4가지 겹침 유형을 비교해 #2와 같은 원인으로 통합
- **심각도·유형 결정:** #5는 minor 결함으로, #6은 서버 동작은 정상이므로 기능 결함이 아닌 사용성 개선 제안(enhancement)으로 분류

## 6. 핵심 인사이트 (v1.0)

### 6-1. AI TC 리뷰: AI가 잘한 것과 사람이 채워야 한 것

**AI가 잘한 것**
- 명세에 적힌 경계값(체크인 당일, 30박, 0박)과 입력 규칙 TC를 잘 만들었고, 실제로 입력 규칙 결함 #5를 찾았습니다 (TC-23).
- 명세가 모호한 부분은 가정을 명시했습니다 (TC-02의 최저가 기준).

**사람이 채워야 한 것**
- **여러 기능에 걸친 결함은 QA가 추가한 TC에서만 나왔습니다.** 화면 간 금액 일치(#1, TC-31), 기간 겹침(#2, TC-32), 로그 개인정보(#3, TC-34)가 그 예입니다.
  - 금액 결함 #1은 AI TC-15도 API 응답의 `totalPrice`로 잡았습니다. 하지만 "고객이 화면마다 다른 금액을 본다"는 영향은 화면 간 비교 TC(TC-31)에서만 드러났습니다.
- **명세를 그대로 따라가 API·개발자 관점으로 쏠렸습니다.** 생성 당시 UI 7건, API 23건이었습니다.
- **내부 표기 때문에 바로 실행하기 어려웠습니다.** `D+30`, `객실 2`, `R1`, `data-testid` 같은 표기에서 리뷰 중 실제로 해석 혼동이 있었습니다.
- **명세에 없는 조건을 기대결과로 넘겨짚었습니다.** TC-04·08·09는 `error.details`에 특정 키가 있어야 한다고 기대했지만, 명세에는 그런 조건이 없었습니다. 자동화 실행에서 Fail로 드러났고, 리뷰 후 결함이 아니라 TC 문제로 판단해 조건을 뺐습니다.

### 6-2. 기간 겹침 4유형 패턴 분석 (#2)

AI는 기간 겹침 중 "뒤쪽 겹침" 1가지만 만들었습니다. 나머지 3가지 유형을 추가해 같은 방식(예약 화면 URL로 직접 진입 → 서버 검증 확인)으로 비교했습니다.

| TC | 유형 | 기존 예약 | 시도 기간 | 체크인 위치 | 결과 |
|---|---|---|---|---|---|
| TC-32 | 앞쪽 겹침 | 11/1 ~ 11/3 | 10/31 ~ 11/2 | 기존 예약 **이전** | ❌ 중복 예약 생성 |
| TC-37 | 감싸기 | 11/1 ~ 11/3 | 10/31 ~ 11/4 | 기존 예약 **이전** | ❌ 중복 예약 생성 |
| TC-38 | 포함 | 11/1 ~ 11/3 | 11/1 ~ 11/2 | 기존 예약 **안** | ✅ 409 차단 |
| TC-17 | 뒤쪽 겹침 | 11/1 ~ 11/3 | 11/2 ~ 11/4 | 기존 예약 **안** | ✅ 409 차단 |

※ 날짜는 예시이며, 자동화는 같은 상대 위치를 실행일 기준 "오늘+n일"로 계산합니다.

- **패턴:** 체크인 날짜가 기존 예약보다 앞이면 겹쳐도 예약이 허용되고, 기존 예약 안에 있으면 차단됩니다.
- 처음엔 TC-37을 별도 결함으로 볼 수도 있었지만, 4가지를 비교해 **같은 원인의 결함 하나**로 묶고 #2의 제목을 패턴에 맞게 바꿨습니다.
- 객실 목록 화면은 4가지 유형 모두 "예약 불가"로 정상 표시했습니다. **화면만 검증했다면 놓쳤을 결함**입니다.

### 6-3. 수동 테스트로만 찾은 #6

TC-36(예약 완료 후 뒤로 가기·새로고침)은 **Pass**입니다. 재제출 2회 모두 서버가 409로 막았고 추가 예약도 없었습니다.
자동화로 상태 코드와 DB만 확인했다면 여기서 끝났을 케이스입니다.

직접 화면을 보니 사용자 입장에서 문제가 있었습니다.
- 뒤로 가기를 하면 버튼이 "예약 처리 중..."에 멈춰 있습니다.
- 새로고침 후 제출하면 "이미 예약된 객실입니다" 에러가 떠서, 방금 예약한 사용자가 **예약에 실패한 것으로 오해**할 수 있습니다.

기능 결함은 아니지만 사용성 개선 제안(#6)으로 등록했습니다. 자동화는 정해 둔 기대결과를 반복해서 확인하는 데 강하고, 기대결과 밖의 사용자 경험은 사람이 직접 봐야 찾을 수 있었습니다.

## 7. v1.1 회원 기능 QA

v1.1에서 회원가입·로그인, 카카오·구글 소셜 로그인(Mock OAuth), 회원 예약, 비회원 예약 허용 스위치가 추가되었습니다.
v1.0과 같은 방식(AI TC 초안 → QA 리뷰·보완 → 실행·자동화)으로 진행했습니다. 상세 기록은 [회귀 테스트 기록](docs/REGRESSION_v1.1.md)에 있습니다.

### 7-1. 회귀 테스트 (v1.0 자동화 26건)

v1.0 테스트를 **하나도 고치지 않고** v1.1에 실행한 뒤, 깨진 테스트를 원인별로 분류했습니다.

| 분류 | 건수 | 내용 |
|---|---:|---|
| 결과 그대로 | 25 | Pass 20, 알려진 결함 5건(#1·#2·#5)은 v1.1에서도 같은 값으로 재현 |
| A. 명세 변경 | 1 | **TC-09**: API는 정상. 로그 형식에 `user=` 추가, 에러 응답에 `details` 추가로 테스트의 로그 검색 조건이 맞지 않음 → 테스트를 1.1 기준으로 수정 후 Pass |
| B. 새 버그 / C. 애매함 | 0 | |

- v1.1 명세에 "`VALIDATION_ERROR`는 항상 `details` 포함"이 추가되었습니다. 그래서 v1.0 리뷰에서 "명세에 없는 조건"으로 뺐던 TC-04·08·09의 `details` 검증을 복구했습니다. **AI 원문 기대결과가 결과적으로 v1.1 명세와 일치**하게 된 사례입니다.
- 탐색 테스트로 #1(금액)·#3(로그 개인정보)·#5(전화번호)가 v1.1에서도 재현되는 것을 확인했습니다.

- TC-64(세션 만료): 자동화와 같은 결과가 재현되었습니다. 안내 없이 비회원 예약으로 저장되었고, 재로그인 후 회원 예약 내역에 나오지 않았습니다(#8).
- TC-66(로그아웃 후 뒤로 가기): 서버는 정상 차단해 기대결과는 Pass입니다. 다만 **자동화에서는 보이지 않던 캐시 화면이 실제 Chrome에서는 개인정보와 함께 그대로 보여** 개선 제안 #12로 등록했습니다(#6과 같은 계열).

### 7-4. 인사이트: 명세가 자세해져도 결함은 명세 밖에서 나왔다

v1.1 명세는 에러 코드, 인증 방식, OAuth 흐름까지 자세히 적혀 있었습니다. 그래서 **AI TC 23건은 수정이 1건뿐이었고, AI 원문 기대결과 기준으로 전부 Pass**였습니다.
반면 **새로 나온 문제 4건은 전부 QA가 추가한 TC에서 발견**되었습니다. 모두 명세가 다루지 않은 상황이었습니다. (머지 후 실제 Chrome 확인에서 찾은 #12도 QA가 추가한 TC-66에서 나왔습니다.)

| 결함 | 명세 밖 상황 | 명세가 말하는 것 / 말하지 않는 것 |
|---|---|---|
| #7 | **UI 우회**: 로그인 상태에서 API로 다른 이메일을 보냄 | "이메일은 계정 이메일로 고정"은 화면 흐름 단락의 문장. 서버도 고정하는지는 없음 |
| #8 | **세션 만료**: 입력 화면을 띄워 둔 채 세션이 끝남 | "로그인이면 MEMBER, 아니면 GUEST"만 있고, 화면에서 만료됐을 때의 안내는 없음 |
| #9 | **반복 실패**: 같은 계정에 틀린 비밀번호를 연속 입력 | 실패 응답 형식만 있고 횟수 제한 정책은 없음 |
| #10 | **에러 콜백**: 로그인 성공 뒤 같은 흐름의 취소 콜백 | "콜백 → state 검증"은 있지만 error 콜백에 대한 언급은 없음 |

AI는 명세에 적힌 규칙을 확인하는 TC는 잘 만들었습니다. 반면 "적혀 있지 않은 상황에서 시스템이 어떻게 동작하는가"를 묻는 TC는 v1.0에 이어 v1.1에서도 사람이 채워야 했습니다.
v1.0의 #2(기간 겹침)와 v1.1의 #7은 **화면 검증만 있고 서버 검증이 없는** 같은 유형입니다. 두 결함 모두 화면을 거치지 않고 서버에 직접 요청하는 UI 우회 테스트로 드러났습니다.

### 7-5. #10을 찾은 과정: 수동 탐색 → 로그 분석 → 재현 → 명세 대조

1. **수동 탐색:** 예약 화면에서 카카오 로그인 중 Mock 화면에서 취소를 눌렀는데, 로그인 상태가 되어 있었습니다.
2. **로그 시간순 분석:** `app.log`를 시간순으로 보니 취소 콜백(17:32:37)보다 4초 앞서 같은 흐름의 로그인 성공 콜백(17:32:33)이 이미 처리되어 있었습니다. 취소 콜백은 `OAUTH_CANCELLED`로 처리되었고, 그 사이에 새 `start` 요청이 없었습니다. 즉 **이미 사용한 state로 온 콜백이 통과**한 것입니다.
    ```
    17:32:32 GET /api/auth/oauth/kakao/start   ...                           ← state 발급 (이후 새 발급 없음)
    17:32:33 GET .../kakao/callback {"code","state"}  → 로그인 성공
    17:32:37 GET .../kakao/callback {"error":"access_denied","state"} user=4 → OAUTH_CANCELLED
    17:32:38 GET /api/cities user=4                                           ← 예약 화면이 아닌 홈으로 이동
    ```
3. **재현:** API로 조건을 나눠 비교했습니다. 같은 조건(state 쿠키 없음, 위조된 state)에서 **code 콜백은 `INVALID_STATE`로 막히지만 error 콜백은 `OAUTH_CANCELLED`로 통과**했습니다.
4. **명세 대조:** 명세 126행 "콜백 → state 검증"에 error 콜백 예외가 없고, 132행이 `INVALID_STATE`를 "state 쿠키 없음/불일치 (CSRF 방어)"로 정의합니다. 이를 근거로 기대값을 `INVALID_STATE`로 정하고 결함으로 등록했습니다. 정상 흐름의 취소(TC-49)는 대조군으로 `OAUTH_CANCELLED`를 유지합니다.

AI TC-50은 code 콜백의 state 불일치만 다뤘습니다. 그래서 이 경로는 탐색 테스트가 아니었다면 놓쳤을 것입니다.

## 8. 테스트 실행 방법

**요구사항:** Node.js 20 이상 (Playwright 1.64의 요구 버전)

```bash
npm install
npx playwright install chromium   # 최초 1회
```

| 명령 | 설명 |
|---|---|
| `npm test` | UI·API 전체 실행 (브라우저 창 없이) |
| `npm run test:watch` | UI 테스트를 브라우저 창을 띄워 실행. `SLOWMO=700 npm run test:watch`처럼 쓰면 동작마다 0.7초씩 쉬어서 눈으로 따라가기 좋음 |
| `npm run test:debug-ui` | Playwright UI 모드. 단계별 화면 스냅샷, 네트워크 요청·응답 확인 |
| `npm run test:report` | 마지막 실행 결과 HTML 리포트 |

- 테스트는 매 실행마다 **DB를 초기화한 전용 서버 3개**를 자동으로 띄웁니다. 환경 변수로 동작이 바뀌는 기능(회원 전용 모드, 세션 만료)을 같은 실행 안에서 검증하기 위해서입니다. 수동 테스트용 서버(`npm start`, 포트 3000)의 데이터에는 영향이 없습니다.

| 서버 | 포트 | 설정 | DB / 로그 | 테스트 |
|---|---|---|---|---|
| 기본 | 3100 | 비회원 예약 허용, 세션 7일 | `data/e2e.db` / `logs/e2e/` | `tests/ui`, `tests/api` |
| 회원 전용 | 3101 | `GUEST_CHECKOUT=off` | `data/e2e-guest-off.db` / `logs/e2e-guest-off/` | `tests/guest-off` (TC-58) |
| 세션 1분 | 3102 | `SESSION_TTL_MINUTES=1` | `data/e2e-short-session.db` / `logs/e2e-short-session/` | `tests/short-session` (TC-46, 64) |

- 세션 만료·OAuth code 만료 확인은 61초씩 기다리므로 전체 실행에 약 75초 걸립니다 (병렬 실행).
- 로그인이 필요한 테스트는 테스트마다 새 회원을 가입시켜 사용합니다. 가입·로그인은 일회용 요청 컨텍스트에서 하고, 토큰은 `Authorization: Bearer`로 명시해서 씁니다 (Playwright `request` 픽스처가 쿠키를 저장해 의도치 않게 로그인 상태가 되는 것을 막기 위해).
- 날짜는 하드코딩하지 않고 실행일 기준 "오늘+n일"로 계산하므로, 언제 실행해도 같은 결과가 나옵니다.
- 테스트가 병렬로 실행되므로 TC마다 서로 다른 객실·기간·계정을 사용해 데이터가 겹치지 않게 했습니다.
- **CI:** main에 push하면 GitHub Actions([워크플로](.github/workflows/playwright.yml))가 같은 테스트를 실행하고, HTML 리포트를 [GitHub Pages](https://sophiachae.github.io/hotel-booking-qa/)에 올립니다. 알려진 결함 9건(v1.0 5건, v1.1 4건)은 `test.fail()`로 표시되어 있어, 배지가 초록색이면 "새로운 실패 없음"을 뜻합니다.
- 앱을 직접 실행하는 방법은 [앱 명세](docs/SPEC.md#1-실행-방법)를 참고하세요.

    - 가운데 공백 허용은 권장 방향으로 보고, 앞뒤 공백은 정책 확인 필요
